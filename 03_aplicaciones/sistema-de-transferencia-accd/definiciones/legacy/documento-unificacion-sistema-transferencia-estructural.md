# Documento de unificación — Sistema de Transferencia Estructural

## 0. Propósito del documento

Este documento presenta la unificación conceptual del mecanismo formado por:

- `modelo_base`
- `instancia_contextual`
- `adaptador / protocolo`
- `codominio`
- `manifestacion_codominial`

Su objetivo no es redefinir cada parte de manera aislada. Las definiciones particulares de cada componente deben consultarse en los documentos especializados correspondientes dentro del artefacto. La función de este documento es explicar **cómo trabajan en conjunto** para permitir el paso desde un plano interno de organización cognitiva hacia un plano externo de manifestación.

El mecanismo puede entenderse como una arquitectura mínima de mediación entre:

```txt
plano_interno_del_sistema
  → estructuras cognitivas, grafos, regiones, modelos, patrones, campos atencionales

plano_externo_de_manifestacion
  → videos, carruseles, clases, newsletters, productos, landings, hilos, piezas, artefactos
```

La pregunta central que responde este documento es:

> ¿Cómo puede una estructura interna del sistema convertirse en un objeto externo válido, sin perder su organización estructural y sin depender de improvisación?

La respuesta es:

> mediante un sistema de transferencia estructural compuesto por modelo base, instancia contextual y adaptador/protocolo, orientado por un codominio y realizado como manifestación codominial.

---

## 1. Nombre del mecanismo

El nombre provisional más directo es:

```txt
sistema_de_transferencia_estructural
```

Este nombre es útil porque enfatiza que el sistema no se limita a “generar contenido”. Su función es transferir una organización estructural desde un plano interno hacia una forma externa.

También pueden usarse nombres alternativos según el contexto:

```txt
mecanismo_de_transferencia_estructural
mecanismo_de_proyeccion_estructural
sistema_de_proyeccion_codominial
arquitectura_de_transferencia_interno_externo
sistema_de_materializacion_estructural
```

La formulación recomendada para este proyecto es:

```txt
Sistema de Transferencia Estructural
```

porque conserva tres ideas importantes:

1. **Sistema**: no se trata de una pieza aislada, sino de una coordinación de componentes.
2. **Transferencia**: el punto central es pasar una estructura de un plano a otro.
3. **Estructural**: no se transfiere solo contenido superficial, sino organización, relaciones, valores, restricciones y forma.

---

## 2. Definición general del Sistema de Transferencia Estructural

Un **Sistema de Transferencia Estructural** es el conjunto operativo mediante el cual una estructura interna del sistema es:

1. hecha inteligible mediante un `modelo_base`;
2. configurada de manera situada mediante una `instancia_contextual`;
3. proyectada hacia un `codominio` mediante un `adaptador / protocolo`;
4. y realizada externamente como una `manifestacion_codominial`.

Puede representarse así:

```txt
estructura_interna
  ↓
modelo_base
  ↓
instancia_contextual
  ↓
adaptador / protocolo
  ↓
codominio
  ↓
manifestacion_codominial
```

O de forma más compacta:

```txt
modelo_base + instancia_contextual + adaptador/protocolo
  → transferencia_estructural
  → manifestacion_codominial
```

La estructura interna puede provenir de:

- un grafo conceptual;
- un grafo atencional;
- un grafo receptoral;
- un grafo identitario;
- un grafo de materialización;
- un campo atencional;
- una entidad federada;
- una arquitectura comercial;
- una teoría;
- un conjunto de casos;
- una configuración estratégica;
- un patrón isomórfico;
- o cualquier estructura cognitiva organizada.

La manifestación externa puede tomar la forma de:

- video corto;
- video largo;
- carrusel;
- newsletter;
- clase;
- producto;
- landing;
- hilo;
- documento;
- guión;
- secuencia;
- interfaz;
- experiencia;
- o cualquier salida compatible con un codominio definido.

---

## 3. Tesis central del mecanismo

La tesis central es la siguiente:

> Una estructura interna no debe saltar directamente a una salida externa. Debe pasar por una forma de inteligibilidad, una configuración contextual y una proyección codominial.

Esto evita el salto insuficiente:

```txt
idea / grafo / estructura interna
  → salida improvisada
```

Y lo reemplaza por una mediación estructurada:

```txt
estructura interna
  → modelo_base
  → instancia_contextual
  → adaptador / protocolo
  → manifestacion_codominial
```

La ventaja es que el resultado externo deja de ser una ocurrencia local y se convierte en una manifestación trazable, reutilizable, auditable y formalmente compatible con una familia de salidas.

---

## 4. Relación con el plano interno y el plano externo

El mecanismo separa dos planos:

## 4.1. Plano interno

El plano interno contiene estructuras que todavía no son objetos externos.

Ejemplos:

```txt
grafo_conceptual
grafo_atencional
grafo_receptoral
grafo_identitario
grafo_de_materializacion
campo_atencional
subgrafo
region_de_grafo
patron_isomorfico
modelo_base
```

Estas estructuras pueden tener organización, pesos, relaciones, jerarquías, tensiones, trayectorias y posibilidades de proyección, pero todavía no son una pieza final.

## 4.2. Plano externo

El plano externo contiene objetos ya manifestados.

Ejemplos:

```txt
guion_de_video_corto
secuencia_de_laminas
newsletter
clase
landing
hilo
producto
video_largo
```

Estas salidas ya tienen forma codominial. No son solo ideas; son objetos externos configurados para un medio, una función y una estructura de uso.

## 4.3. Mediación

El Sistema de Transferencia Estructural media entre ambos planos.

Su función es garantizar que lo externo no sea una deformación arbitraria de lo interno, sino una proyección estructuralmente controlada.

---

## 5. Responsabilidad transversal del sistema

La responsabilidad transversal del sistema no es producir una salida cualquiera.

Su responsabilidad es:

> preservar estructura durante el paso de un plano interno a un plano externo.

Esto implica conservar, traducir o proyectar:

- relaciones;
- jerarquías;
- pesos;
- funciones;
- tensiones;
- restricciones;
- roles;
- modos de presencia;
- decisiones contextuales;
- condiciones receptorales;
- dinámicas atencionales;
- exigencias formales de salida;
- y criterios de validez codominial.

La salida puede cambiar de forma según el codominio, pero no debe perder el orden estructural que la originó.

---

## 6. Estructura funcional del mecanismo

El mecanismo tiene cinco momentos funcionales.

## 6.1. Inteligibilización

La estructura interna debe poder ser leída bajo un modelo.

Esto ocurre mediante el `modelo_base`.

El modelo base no produce la salida. Hace posible que múltiples casos distintos puedan describirse bajo una estructura común.

## 6.2. Configuración

Un caso particular selecciona valores dentro del espacio definido por el modelo base.

Esto ocurre mediante la `instancia_contextual`.

La instancia contextual no es todavía la salida. Es una configuración situada y operable.

## 6.3. Proyección

La instancia contextual se entrega a un adaptador.

El adaptador interpreta sus valores mediante reglas, protocolos o procedimientos de composición.

## 6.4. Codominialización

La salida no se produce en abstracto, sino dentro de un codominio.

El codominio define qué forma de salida es válida.

Por ejemplo:

```txt
video_corto → guion audiovisual breve con bloques
carrusel → secuencia visual por laminas
newsletter → pieza escrita distribuida
clase → secuencia didactica
landing → estructura de conversion
```

## 6.5. Manifestación

Finalmente aparece una manifestación codominial.

Esta manifestación es el objeto externo producido por el adaptador dentro del codominio.

---

## 7. Fórmula general del sistema

Una formulación abstracta del mecanismo puede expresarse así:

```txt
M = modelo_base
I = instancia_contextual
A = adaptador / protocolo
C = codominio
Y = manifestacion_codominial
```

Entonces:

```txt
I ∈ M
```

Es decir, la instancia contextual pertenece al espacio de configuraciones permitido por el modelo base.

Y:

```txt
A(I) → Y
```

Es decir, el adaptador transforma la instancia contextual en una manifestación codominial.

Además:

```txt
Y ∈ C
```

Es decir, la manifestación codominial pertenece al codominio especificado.

La forma completa sería:

```txt
A_C(I_M) → Y_C
```

Donde:

- `I_M` es una instancia contextual construida desde el modelo base `M`;
- `A_C` es un adaptador orientado al codominio `C`;
- `Y_C` es una manifestación codominial válida dentro de `C`.

## 8. Relación con grafos y regiones de grafos

Dentro de la ACCD, una estructura interna puede estar organizada como grafo.

Ese grafo puede contener:

- nodos conceptuales;
- nodos atencionales;
- nodos receptorales;
- nodos identitarios;
- nodos comerciales;
- nodos de recursos;
- nodos de evidencia;
- relaciones de soporte;
- relaciones de contraste;
- relaciones de consecuencia;
- relaciones de dependencia;
- relaciones de isomorfismo;
- relaciones de pertenencia;
- relaciones de derivación.

Sin embargo, un adaptador no necesita consumir el grafo completo.

Lo que suele ocurrir es:

```txt
grafo
  → region_de_grafo
  → instancia_contextual
  → adaptador
  → manifestacion_codominial
```

O, cuando intervienen varios grafos:

```txt
region_del_grafo_conceptual
region_del_grafo_atencional
region_del_grafo_receptoral
region_del_grafo_identitario
region_del_grafo_de_materializacion
        ↓
instancia_contextual
        ↓
adaptador
        ↓
manifestacion_codominial
```

Aquí la instancia contextual funciona como condensador intergrafal.

No contiene todos los grafos, sino una configuración de valores derivada de regiones seleccionadas de esos grafos.

---

## 9. Instancia contextual como condensador estructural

Aunque el documento específico de `instancia_contextual` desarrolla su definición particular, en este documento de unificación conviene resaltar su función transversal:

> la instancia contextual condensa una configuración particular que puede provenir de distintas estructuras internas y la vuelve legible para un adaptador.

Por eso, la instancia contextual es el punto donde se encuentran:

- la estructura interna;
- el modelo base;
- el contexto de proyección;
- las condiciones del adaptador;
- y la futura salida.

Su importancia está en que permite que una estructura interna sea convertida en una entrada operable.

Sin instancia contextual, el adaptador tendría que interpretar directamente el grafo o la idea en crudo.

Eso sería menos controlable, menos auditable y menos reusable.

---

## 10. Adaptador como función codominial

El adaptador no debe entenderse como una plantilla de salida ni como una simple instrucción de estilo.

En el sistema unificado, el adaptador cumple una función más precisa:

> transformar una instancia contextual en una manifestación codominial válida.

Esto significa que el adaptador debe conocer:

- qué tipo de instancia recibe;
- qué campos de la instancia son relevantes;
- qué valores activan qué contribuciones;
- qué codominio gobierna la salida;
- qué forma debe tener la manifestación;
- qué restricciones no puede romper;
- y qué criterios permiten evaluar la validez del resultado.

Un adaptador puede especializarse en distintos codominios:

```txt
adaptador_video_corto
adaptador_video_largo
adaptador_carrusel
adaptador_newsletter
adaptador_clase
adaptador_producto
adaptador_landing
adaptador_hilo
```

Todos pueden compartir una lógica general:

```txt
instancia_contextual
  → adaptador_especifico
  → manifestacion_codominial
```

Pero cada uno aplica reglas codominiales distintas.

---

## 11. Codominio como especificación de forma posible

El codominio no es una pieza concreta.

Tampoco es simplemente un tema.

El codominio es el espacio de formas válidas que una manifestación puede tomar bajo un adaptador determinado.

Por eso, el codominio debe entenderse como una especificación estructural de salida.

Por ejemplo:

```txt
codominio_video_corto:
  familia: guion_audiovisual_breve
  unidades: bloques
  capas: verbal, visual, escenica, auditiva
  restricciones: brevedad, ritmo, apertura, cierre

codominio_carrusel:
  familia: secuencia_de_laminas
  unidades: slides
  capas: texto, visualidad, progresion, cierre
  restricciones: sintesis, legibilidad, guardabilidad

codominio_clase:
  familia: secuencia_didactica
  unidades: momentos_de_aprendizaje
  capas: explicacion, ejemplo, recapitulacion, ejercicio
  restricciones: continuidad, claridad, progresion
```

La manifestación codominial es una realización concreta dentro de ese espacio.

---

## 12. Manifestación codominial como objeto externo

La manifestación codominial es el resultado final del mecanismo.

No es el modelo base.
No es la instancia contextual.
No es el adaptador.
No es el codominio.

Es la salida concreta producida por el adaptador en un codominio.

Puede ser simple o compuesta.

Una manifestación simple puede ser:

```txt
un_titulo
un_post
una_lamina
una_respuesta
```

Una manifestación compuesta puede ser:

```txt
guion_de_video_corto:
  cabecera
  macroestructura
  bloques
  capa_verbal
  capa_visual
  capa_escenica
  capa_auditiva
  justificacion_de_composicion
```

La manifestación codominial es la forma en que una estructura interna se vuelve externa, utilizable, visible y distribuible.

## 13. Principio de no sustitución entre componentes

Un error frecuente consiste en hacer que un componente absorba la responsabilidad de otro.

Este sistema evita ese error mediante separación funcional.

## 13.1. El modelo base no sustituye a la instancia

El modelo base define posibilidades.

La instancia contextual selecciona una configuración particular.

## 13.2. La instancia no sustituye al adaptador

La instancia fija valores.

El adaptador transforma esos valores en una salida.

## 13.3. El adaptador no sustituye al codominio

El adaptador opera hacia un codominio.

El codominio define la familia de formas válidas.

## 13.4. El codominio no sustituye a la manifestación

El codominio define el espacio de salida.

La manifestación codominial es un elemento particular dentro de ese espacio.

## 13.5. La manifestación no sustituye al sistema

La manifestación es el resultado visible.

No debe confundirse con el mecanismo que la produjo.

---

## 14. Principios transversales del Sistema de Transferencia Estructural

## 14.1. Separación de planos

El sistema distingue entre plano interno y plano externo.

Esto evita tratar una idea, grafo o subgrafo como si ya fuera una pieza final.

## 14.2. Inteligibilidad previa

Antes de proyectar una estructura, debe poder ser descrita bajo un modelo base.

## 14.3. Configuración situada

Ninguna salida debe producirse directamente desde el modelo general.

Debe pasar por una instancia contextual.

## 14.4. Proyección codominial

Toda salida debe pertenecer a un codominio.

Esto garantiza que tenga forma, restricciones y criterios de validez.

## 14.5. Trazabilidad

Debe poder rastrearse qué configuración produjo qué parte de la manifestación.

## 14.6. Reusabilidad

Un mismo modelo base puede producir múltiples instancias.

Una misma instancia puede ser proyectada por adaptadores distintos.

Un mismo adaptador puede recibir múltiples instancias compatibles.

## 14.7. Isomorfismo

Casos distintos pueden compartir estructura.

El sistema permite reutilizar modelos, instancias parciales, configuraciones y adaptadores cuando la forma estructural se conserva.

## 14.8. Auditabilidad

Si una salida falla, el sistema permite preguntar dónde está el problema:

```txt
¿falló el modelo base?
¿falló la instancia contextual?
¿falló el adaptador?
¿falló la especificación codominial?
¿falló la manifestación concreta?
```

## 14.9. Modularidad

Cada componente puede refinarse sin destruir necesariamente los demás.

## 14.10. Extensibilidad

El sistema permite añadir nuevos codominios, adaptadores o modelos base sin abandonar la arquitectura general.

## 15. Importancia para la ACCD

Dentro de la ACCD, este mecanismo es fundamental porque evita que la creación de contenido sea entendida como una operación directa de generación textual.

La ACCD busca producir contenido como resultado de una arquitectura:

```txt
grafos / campos / estructuras internas
  → instancias contextuales
  → adaptadores
  → manifestaciones codominiales
  → recepción / evidencia / retorno
```

El Sistema de Transferencia Estructural es el núcleo que permite la fase:

```txt
estructura interna
  → manifestación externa
```

Sin este mecanismo, la ACCD correría el riesgo de operar como un conjunto de prompts aislados.

Con este mecanismo, la ACCD puede operar como una arquitectura de producción estructural.

---

## 16. Relación con entidades federadas

El mecanismo también permite entender cómo puede operar una entidad federada.

Una entidad federada puede contener múltiples grafos, ramas, adaptadores y manifestaciones.

Pero para que esas partes no sean sistemas aislados, deben compartir un mecanismo de transferencia.

Por ejemplo:

```txt
nucleo_portable
  → grafo_conceptual
  → subgrafos
  → instancias_contextuales
  → adaptadores
  → manifestaciones
```

Cada rama puede producir una salida distinta, pero todas pueden conservar relación con un mismo núcleo estructural.

El Sistema de Transferencia Estructural permite que la entidad federada no sea una suma de piezas, sino una arquitectura coherente de proyecciones diferenciadas.

---

## 17. Relación con la idea de función de varias variables

El mecanismo puede entenderse como una función compuesta.

La instancia contextual tiene dimensiones y campos.

Cada dimensión puede pensarse como una variable estructurada.

Cada campo puede pensarse como una coordenada interna.

Cada valor puede pensarse como una selección concreta.

Así, el adaptador recibe algo parecido a:

```txt
adaptador(
  vector_dimension_1,
  vector_dimension_2,
  vector_dimension_3,
  ...,
  vector_dimension_n
)
→ manifestacion_codominial
```

Pero no se trata de una función matemática simple.

Cada vector puede provenir de regiones de grafos, configuraciones contextuales y decisiones de proyección.

Una formulación más adecuada sería:

```txt
adaptador_especifico(
  instancia_contextual
) → manifestacion_codominial
```

Donde la instancia contextual ya condensa los vectores necesarios.

## 18. Patrón de uso general

Una IA que reciba un artefacto con estos documentos debe entender el patrón de uso de la siguiente manera.

## 18.1. Identificar el modelo base

Primero debe reconocer qué modelo base está activo y qué dimensiones/campos define.

## 18.2. Identificar o construir la instancia contextual

Después debe verificar si ya existe una instancia contextual.

Si no existe, debe ayudar a construirla seleccionando valores válidos dentro del modelo base.

## 18.3. Identificar el adaptador

Luego debe reconocer qué adaptador/protocolo se usará.

Por ejemplo:

```txt
adaptador_video_corto
adaptador_carrusel
adaptador_clase
```

## 18.4. Identificar el codominio

Debe revisar qué forma de salida exige el codominio.

No debe producir una salida genérica.

## 18.5. Producir la manifestación codominial

Finalmente debe aplicar el adaptador a la instancia contextual y producir una manifestación válida.

---

## 19. Patrón de validación

Una salida del sistema debe evaluarse con preguntas como:

```txt
¿La instancia contextual usa valores permitidos por el modelo base?
¿El adaptador recibió una instancia suficientemente determinada?
¿El codominio está claro?
¿La manifestación pertenece realmente al codominio?
¿La salida conserva la estructura de entrada?
¿Las decisiones son trazables?
¿Se distingue entre modelo, instancia, adaptador, codominio y manifestación?
```

Si alguna respuesta es negativa, el sistema debe revisarse antes de considerar válida la salida.

---

## 20. Diferencia entre generación y transferencia estructural

Este documento debe dejar clara una diferencia fundamental.

Generar contenido puede significar simplemente producir una pieza.

Transferir estructura significa producir una pieza que conserva una relación controlada con una organización interna previa.

La ACCD no busca solo generación.

Busca transferencia estructural.

Por eso, el resultado no debe evaluarse únicamente por si “suena bien” o “parece útil”.

Debe evaluarse por si:

- conserva estructura;
- respeta la configuración;
- cumple el codominio;
- hace visibles las decisiones relevantes;
- y puede reutilizarse o corregirse dentro del sistema.

## 21. Ejemplo abstracto del mecanismo completo

Supongamos un modelo base abstracto:

```txt
modelo_base_X:
  dimension_1:
    campo_1_1:
      valores_posibles:
        - valor_1_1_a
        - valor_1_1_b
        - valor_1_1_c

  dimension_2:
    campo_2_1:
      valores_posibles:
        - valor_2_1_a
        - valor_2_1_b

  dimension_3:
    campo_3_1:
      valores_posibles:
        - valor_3_1_a
        - valor_3_1_b
        - valor_3_1_c
```

Una instancia contextual podría ser:

```txt
instancia_contextual_X_01:
  modelo_base: modelo_base_X

  dimension_1:
    campo_1_1: valor_1_1_b

  dimension_2:
    campo_2_1: valor_2_1_a

  dimension_3:
    campo_3_1: valor_3_1_c
```

Un adaptador podría proyectarla hacia un codominio:

```txt
adaptador_Y:
  entrada: instancia_contextual_X_01
  codominio: codominio_Y
  salida: manifestacion_codominial_Y_01
```

La salida no es una copia de la instancia. Es una realización externa que pertenece al codominio.

## 22. Ejemplo dentro de contenido digital

Una estructura interna puede estar organizada como grafo conceptual y grafo atencional.

```txt
grafo_conceptual:
  region_A: ideas principales del tema

grafo_atencional:
  region_B: estrategia de captacion y retencion
```

Ambas regiones pueden condensarse en una instancia contextual:

```txt
instancia_contextual_video_corto:
  dimension_construccion_del_caso:
    fuente: region_A_del_grafo_conceptual

  dimension_dinamica_atencional:
    fuente: region_B_del_grafo_atencional
```

Luego un adaptador de video corto produce:

```txt
manifestacion_codominial_video_corto:
  guion
  bloques
  texto_oral
  texto_en_pantalla
  indicaciones_escenicas
  recursos_visuales
```

Esto muestra cómo el sistema permite pasar de regiones internas de grafos a una pieza externa concreta.

Una IA que lea este documento debe comprender que:

1. El sistema no es una plantilla de contenido.
2. El sistema es un mecanismo de transferencia estructural.
3. El modelo base hace inteligibles familias de casos.
4. La instancia contextual fija una configuración particular.
5. El adaptador/protocolo proyecta esa configuración hacia un codominio.
6. El codominio define el espacio formal de salida.
7. La manifestación codominial es el objeto externo producido.
8. La salida debe conservar trazabilidad respecto de la estructura interna.
9. La ACCD puede usar este mecanismo en muchos adaptadores distintos.
10. La arquitectura es extensible, reusable y compatible con entidades federadas.

## 26. Cierre conceptual

El Sistema de Transferencia Estructural puede resumirse así:

> Una estructura interna del sistema no se manifiesta directamente. Primero debe hacerse inteligible mediante un modelo base; después debe configurarse como instancia contextual; luego debe proyectarse mediante un adaptador/protocolo hacia un codominio; finalmente aparece como manifestación codominial. Este mecanismo permite que la ACCD transforme grafos, campos, patrones y estructuras cognitivas internas en objetos externos válidos, trazables y reutilizables.

La fórmula final es:

```txt
estructura_interna
  → modelo_base
  → instancia_contextual
  → adaptador/protocolo
  → codominio
  → manifestacion_codominial
```

Y la función final del sistema es:

> hacer posible la transferencia estructural de un plano interno a un plano externo sin perder inteligibilidad, configuración, trazabilidad ni validez codominial.
