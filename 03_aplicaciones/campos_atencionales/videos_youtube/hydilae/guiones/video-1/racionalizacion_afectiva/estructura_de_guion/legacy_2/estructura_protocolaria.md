# Prompt protocolario estructural para construir el guion sobre racionalización afectiva

**Tipo de documento:** prompt protocolario estructural  
**Tema del guion:** racionalización afectiva  
**Formato destino:** video ensayístico para YouTube  
**Arquitectura base:** transferencia e interiorización del mecanismo  
**Unidad macro:** evento cognitivo  
**Unidad interna:** subevento cognitivo  
**Uso previsto:** adjuntar este protocolo junto con una descripción parcial o total de un evento cognitivo para que una IA construya, refine o instancie el guion respetando la estructura.

**Nota de actualización:** el nombre "racionalización afectiva" queda como rótulo interno de trabajo del proyecto. El Evento Cognitivo 3 ya no debe presentar ese nombre como término académico estabilizado; debe construir un modelo psicológico compuesto apoyado en teorías existentes.

---

# 0. Instrucción central para la IA que use este protocolo

Cuando recibas este documento junto con una descripción del usuario, no debes tratar la descripción como guion final ni como ejemplo definitivo. Debes tratarla como **material de instanciación** de una arquitectura cognitiva ya definida.

Tu tarea consiste en:

```txt
1. Identificar a qué evento cognitivo o subevento cognitivo pertenece el material del usuario.
2. Leer la función estructural de ese componente en este protocolo.
3. Determinar qué estado cognitivo de entrada presupone.
4. Determinar qué operación cognitiva debe realizar.
5. Determinar qué estado cognitivo de salida debe producir.
6. Verificar las transiciones con el componente anterior y posterior.
7. Instanciar, corregir o proponer contenido solo si preserva la función estructural.
8. Declarar cualquier vacío estructural si el material del usuario no cumple una función necesaria.
```

Este protocolo no pide generar contenido libre. Pide **construir contenido bajo reglas de pertenencia, función y transición**.

# 1. Diferencia entre estructura, protocolo e instancia

## 1.1. Estructura del guion

La estructura del guion es la arquitectura base:

```txt
Evento Cognitivo 1 — Caso ancla de reconocimiento
Evento Cognitivo 2 — Generalización humana
Evento Cognitivo 3 — Formalización psicológica basada en teorías existentes
Evento Cognitivo 4 — Diseño deliberado del patrón
Evento Cognitivo 5 — Transferencia publicitaria global
Evento Cognitivo 6 — Demostración en marcas o campañas
Evento Cognitivo 7 — Retorno reflexivo al consumidor
Evento Cognitivo 8 — Regla final memorable
```

## 1.2. Prompt protocolario

El prompt protocolario es la descripción estructural de cómo debe funcionar cada componente:

```txt
evento cognitivo
  → función macro
  → estado de entrada
  → subeventos obligatorios
  → transiciones internas
  → estado de salida
  → criterios de validación
```

## 1.3. Instancia generada

La instancia generada es el contenido concreto que se producirá después:

```txt
ejemplo concreto
escena
fragmento de guion
transición verbal
formulación narrativa
pregunta para audiencia
regla final
```

Este documento todavía no es la instancia. Es el protocolo que permite construirla.

# 2. Regla de jerarquía estructural

La IA debe respetar esta jerarquía:

```txt
Macrotrayectoria del video
  contiene Eventos Cognitivos
    contienen Subeventos Cognitivos
      realizan Operaciones Cognitivas
        producen Cambios de Estado Cognitivo
          habilitan Transiciones
```

Un subevento no debe generarse porque “suena bien”, sino porque cumple una función necesaria dentro del evento cognitivo.

---

# 3. Regla de transformación cognitiva

Todo componente debe poder formularse así:

```txt
estado cognitivo de entrada
  → operación cognitiva
    → estado cognitivo de salida
```

Si una parte propuesta por el usuario no transforma ningún estado cognitivo, entonces no pertenece todavía al guion. Puede servir como material, pero debe ser reubicada, reformulada o descartada.

---

# 4. Regla de transición

Toda transición debe especificar:

```yaml
transicion:
  desde:
  hacia:
  estado_que_recibe:
  estado_que_debe_preservar:
  operacion_de_paso:
  estado_que_habilita:
  riesgo_si_falla:
```

Una transición no es solo una frase de enlace. Es una operación que preserva un estado cognitivo y habilita otro.

---

# 5. Regla de uso de los módulos MAANC

Los módulos MAANC no deben tratarse como etiquetas decorativas. Cada módulo indica qué tipo de operación estructural debe realizarse.

```yaml
uso_de_modulos_MAANC:
  segmentador_funcional:
    funcion: dividir por cambio de responsabilidad funcional

  constructor_de_trayectoria_narrativa:
    funcion: ordenar componentes como transformación progresiva del espectador

  modelador_de_situacion_cognitiva:
    funcion: definir actualizaciones del modelo mental del espectador

  detector_de_estructura_expositiva:
    funcion: organizar definiciones, contrastes, matrices y explicaciones

  analizador_de_moves_retoricos:
    funcion: convertir operaciones cognitivas en acciones discursivas

  analizador_intencional_atencional:
    funcion: fijar qué debe mirar mentalmente el espectador

  analizador_de_relaciones_retoricas:
    funcion: conectar componentes como contraste, preparación, expansión, justificación o cierre

  analizador_argumentativo:
    funcion: controlar claims, soportes, matices, objeciones y riesgos de exageración

  detector_de_esquemas_narrativos:
    funcion: crear plantillas repetibles para casos y ejemplos

  extractor_de_macroestructura:
    funcion: extraer la forma común de varios casos o condensar la tesis mínima

  analizador_de_metadiscurso:
    funcion: crear señales de orientación, recapitulación, prevención de malentendidos y clausura

  integrador_ACCD:
    funcion: compilar componentes en una arquitectura coherente y validable
```

# 6. Macrotrayectoria protocolaria del video

El guion completo debe transformar al espectador de este modo:

```txt
Reconoce un mecanismo en una relación de pareja
  → descubre que el mecanismo aparece en muchas decisiones
    → comprende un modelo psicológico compuesto basado en teorías existentes
      → entiende que esa estructura psicológica puede ser aprovechada por sistemas de diseño simbólico
        → ve cómo la publicidad puede diseñar estado y justificación
          → observa el mecanismo en marcas o campañas
            → vuelve la pregunta sobre sus propias decisiones
              → recibe una regla crítica memorable
```

Estado cognitivo inicial del espectador:

```txt
“Mis decisiones se explican principalmente por las razones que puedo dar.”
```

Estado cognitivo final buscado:

```txt
“Mis razones pueden ser verdaderas y aun así cumplir una función justificativa. Algunas decisiones pueden estar orientadas por afecto, identidad o símbolos y estabilizadas por razones declarables. La publicidad puede intervenir en ambas capas.”
```

# 7. Eventos cognitivos y subeventos cognitivos protocolarios

# Evento Cognitivo 1 — Caso ancla de reconocimiento

```yaml
evento_cognitivo_1:
  nombre: caso_ancla_de_reconocimiento
  frase_guia: "Esto pasa en las parejas"
  funcion_macro: hacer_visible_el_mecanismo_sin_definirlo
```

## Descripción protocolaria del evento

Este evento existe para introducir el mecanismo de racionalización afectiva sin nombrarlo todavía. Su función no es hablar de relaciones de pareja como tema autónomo, sino usar una relación de pareja como **escenario de reconocimiento** donde la audiencia pueda detectar intuitivamente una doble capa:

```txt
lo que alguien dice que lo mueve
vs.
lo que quizá realmente lo sostiene afectivamente
```

## Estado cognitivo de entrada

```txt
El espectador puede reconocer una situación humana cotidiana, pero aún no distingue formalmente razón declarada y fuerza afectiva.
```

## Estado cognitivo de salida

```txt
El espectador sospecha que una decisión puede tener una explicación verbal aceptable y, al mismo tiempo, una causa afectiva más profunda.
```

## Regla de construcción

El material que instancie este evento debe hacer visible el mecanismo sin conceptualizarlo todavía. No debe definir “racionalización afectiva”. No debe convertir el evento en consejo sentimental.

## Subeventos del Evento Cognitivo 1

### Subevento 1.1 — Situación de pareja reconocible

```yaml
subevento_1_1:
  funcion_local: instalar_un_caso_comprensible
  estado_entrada: espectador_sin_modelo_teorico
  operacion_cognitiva: activar_reconocimiento_inmediato
  estado_salida: espectador_dentro_de_un_caso_humano_comprensible
  modulos_MAANC:
    - modelador_de_situacion_cognitiva
    - analizador_intencional_atencional
```

**Descripción protocolaria:**  
Este subevento debe situar al espectador ante una escena o situación que pueda comprender sin explicación previa. El foco no es la relación en sí, sino su utilidad como soporte para ver una operación cognitiva posterior.

**Uso de módulos MAANC:**

- `modelador_de_situacion_cognitiva`: define el estado mental inicial del espectador y asegura que el caso sea reconocible.
- `analizador_intencional_atencional`: impide que la atención se desplace al drama sentimental; dirige el foco hacia la futura doble capa.

**Criterio de validación:**  
Es correcto si el espectador puede decir: “entiendo esta situación”, sin que todavía se le haya dado una teoría.

---

### Transición 1.1 → 1.2

```yaml
transicion_1_1_a_1_2:
  desde: situacion_de_pareja_reconocible
  hacia: razon_declarada_noble_o_aceptable
  estado_que_recibe: reconocimiento_del_caso
  operacion_de_paso: pasar_de_situacion_a_explicacion_verbal
  estado_que_habilita: atencion_a_lo_que_la_persona_dice_sobre_su_decision
```

**Descripción protocolaria:**  
La transición debe llevar al espectador desde la situación hacia la explicación que el sujeto ofrece. No debe introducir todavía sospecha ni contradicción fuerte; solo debe hacer visible la capa verbal.

---

### Subevento 1.2 — Razón declarada noble o aceptable

```yaml
subevento_1_2:
  funcion_local: mostrar_la_explicacion_verbal_visible
  estado_entrada: espectador_reconoce_la_situacion
  operacion_cognitiva: presentar_una_razon_defendible
  estado_salida: espectador_acepta_provisionalmente_la_razon_declarada
  modulos_MAANC:
    - analizador_de_moves_retoricos
    - detector_de_estructura_expositiva
```

**Descripción protocolaria:**  
Este subevento debe presentar la razón que la persona declara para explicar su permanencia, decisión o conducta. La razón debe sonar aceptable, razonable, noble, madura o socialmente defendible.

**Uso de módulos MAANC:**

- `analizador_de_moves_retoricos`: construye el gesto de justificación verbal.
- `detector_de_estructura_expositiva`: ayuda a formular la razón como explicación clara y comprensible.

**Criterio de validación:**  
Es correcto si la razón declarada puede ser aceptada provisionalmente por la audiencia sin parecer absurda.

---

### Transición 1.2 → 1.3

```yaml
transicion_1_2_a_1_3:
  desde: razon_declarada_noble_o_aceptable
  hacia: capa_afectiva_no_declarada
  estado_que_recibe: aceptacion_provisional_de_la_razon
  operacion_de_paso: introducir_duda_sobre_suficiencia_explicativa
  estado_que_habilita: sospecha_de_una_capa_mas_profunda
```

**Descripción protocolaria:**  
La transición debe abrir una fisura: la razón puede ser válida, pero quizá no explica todo. No debe desmentir la razón; debe cuestionar su suficiencia.

---

### Subevento 1.3 — Capa afectiva no declarada

```yaml
subevento_1_3:
  funcion_local: mostrar_que_la_razon_declarada_no_agota_la_decision
  estado_entrada: espectador_acepta_la_razon_declarada
  operacion_cognitiva: introducir_fuerza_afectiva_posible
  estado_salida: espectador_sospecha_una_causa_afectiva_no_declarada
  modulos_MAANC:
    - constructor_de_trayectoria_narrativa
    - modelador_de_situacion_cognitiva
```

**Descripción protocolaria:**  
Este subevento desplaza al espectador de la explicación verbal hacia una posible fuerza afectiva no dicha. Debe sugerir que puede haber miedo, apego, costumbre, identidad o dependencia sosteniendo la decisión.

**Uso de módulos MAANC:**

- `constructor_de_trayectoria_narrativa`: produce el primer desplazamiento interpretativo.
- `modelador_de_situacion_cognitiva`: actualiza el modelo mental del espectador: ahora hay dos niveles posibles.

**Criterio de validación:**  
Es correcto si el espectador piensa: “la razón que dio puede ser cierta, pero quizá no es toda la historia”.

---

### Transición 1.3 → 1.4

```yaml
transicion_1_3_a_1_4:
  desde: capa_afectiva_no_declarada
  hacia: contraste_doble_capa_sin_nombre_tecnico
  estado_que_recibe: sospecha_de_capa_afectiva
  operacion_de_paso: poner_en_relacion_la_razon_y_la_fuerza_afectiva
  estado_que_habilita: percepcion_de_doble_capa
```

**Descripción protocolaria:**  
La transición debe convertir la sospecha en contraste. Ya no basta con insinuar una capa afectiva; ahora debe verse la coexistencia de dos capas en una misma decisión.

---

### Subevento 1.4 — Contraste doble capa sin nombre técnico

```yaml
subevento_1_4:
  funcion_local: hacer_visible_la_diferencia_entre_lo_declarado_y_lo_efectivo
  estado_entrada: espectador_sospecha_una_capa_afectiva
  operacion_cognitiva: contrastar_razon_declarada_y_causa_afectiva
  estado_salida: espectador_percibe_doble_capa_sin_nombre_teorico
  modulos_MAANC:
    - segmentador_funcional
    - analizador_de_relaciones_retoricas
```

**Descripción protocolaria:**  
Este subevento debe poner en paralelo la razón declarada y la fuerza afectiva posible. No debe resolver aún el concepto; solo debe estabilizar la percepción de que hay dos capas.

**Uso de módulos MAANC:**

- `segmentador_funcional`: separa las dos responsabilidades internas: mostrar razón y mostrar fuerza afectiva.
- `analizador_de_relaciones_retoricas`: conecta ambas por contraste dentro de una misma decisión.

**Criterio de validación:**  
Es correcto si el espectador puede distinguir “lo que dice” de “lo que quizá lo mueve”.

---

### Transición 1.4 → 1.5

```yaml
transicion_1_4_a_1_5:
  desde: contraste_doble_capa_sin_nombre_tecnico
  hacia: sospecha_inicial
  estado_que_recibe: percepcion_de_doble_capa
  operacion_de_paso: convertir_contraste_en_pregunta_abierta
  estado_que_habilita: sospecha_interpretativa_estable
```

**Descripción protocolaria:**  
La transición debe dejar el contraste funcionando como pregunta, no como conclusión cerrada. Debe preparar la generalización posterior.

---

### Subevento 1.5 — Sospecha inicial

```yaml
subevento_1_5:
  funcion_local: dejar_abierta_la_pregunta_sobre_la_doble_capa
  estado_entrada: espectador_percibe_doble_capa
  operacion_cognitiva: instalar_sospecha_interpretativa
  estado_salida: espectador_preparado_para_generalizar_el_patron
  modulos_MAANC:
    - analizador_de_metadiscurso
    - analizador_intencional_atencional
```

**Descripción protocolaria:**  
Este subevento debe cerrar el evento cognitivo dejando una pregunta activa: si esto ocurre aquí, ¿dónde más ocurre? Su función es preparar el paso al Evento Cognitivo 2.

**Uso de módulos MAANC:**

- `analizador_de_metadiscurso`: crea la señal de orientación hacia la generalización.
- `analizador_intencional_atencional`: asegura que el espectador salga mirando el mecanismo, no el caso sentimental.

**Criterio de validación:**  
Es correcto si el espectador queda preparado para aceptar que el mecanismo podría aparecer en otros dominios.

```yaml
transicion_evento_1_a_evento_2:
```

Esta transición debe impedir que el caso de pareja quede encerrado en el dominio sentimental. Debe convertirlo en indicio de una estructura más amplia.

# Evento Cognitivo 2 — Generalización humana

```yaml
evento_cognitivo_2:
  nombre: generalizacion_humana
  frase_guia: "Esto pasa en muchas decisiones"
  funcion_macro: convertir_el_caso_inicial_en_patron_general
```

## Descripción protocolaria del evento

Este evento existe para demostrar que el mecanismo visto en la pareja no pertenece solo a relaciones sentimentales. Debe mostrar que la misma forma aparece en dominios distintos: consumo, estatus, vida profesional, identidad, ideología o pertenencia.

## Estado cognitivo de entrada

```txt
El espectador sospecha que una decisión puede tener una capa declarada y una capa afectiva no declarada.
```

## Estado cognitivo de salida

```txt
El espectador comprende que no se trata de un caso aislado, sino de una estructura general de decisión.
```

## Regla de construcción

Los casos deben variar en superficie, pero conservar una forma común:

```txt
estado afectivo o identitario
→ decisión o permanencia
→ razón declarable
→ función justificativa
```

## Subevento 2.1 — Recuperación del patrón de pareja

```yaml
subevento_2_1:
  funcion_local: extraer_la_forma_del_caso_anterior
  estado_entrada: espectador_recuerda_el_caso_de_pareja
  operacion_cognitiva: abstraer_patron_base
  estado_salida: espectador_posee_una_plantilla_reutilizable
  modulos_MAANC:
    - detector_de_esquemas_narrativos
    - segmentador_funcional
```

**Descripción protocolaria:**  
Este subevento debe extraer la forma del caso anterior sin quedarse en sus detalles. Debe convertir el caso de pareja en una plantilla mínima.

**Criterio de validación:**  
Es correcto si el espectador puede identificar la forma: “algo afectivo mueve, algo racional justifica”.

### Transición 2.1 → 2.2

```yaml
transicion_2_1_a_2_2:
  desde: recuperacion_del_patron_pareja

  operacion_de_paso: probar_la_plantilla_en_otro_dominio

```

**Descripción protocolaria:**  
La transición debe decir, de forma explícita o implícita: veamos si esta forma aparece fuera de las relaciones.

## Subevento 2.2 — Caso de consumo o estatus

```yaml
subevento_2_2:
  funcion_local: mostrar_el_mismo_mecanismo_fuera_de_la_pareja
  estado_entrada: espectador_posee_plantilla_base
  operacion_cognitiva: aplicar_plantilla_a_consumo_o_estatus
  estado_salida: espectador_reconoce_repeticion_del_mecanismo
  modulos_MAANC:
    - analizador_argumentativo
    - detector_de_esquemas_narrativos
```

**Descripción protocolaria:**  
Este subevento debe presentar una decisión de consumo o estatus donde la razón declarada pueda coexistir con una motivación afectiva o identitaria. No debe afirmar de forma absoluta que todo consumo es estatus.

**Criterio de validación:**  
Es correcto si el caso repite la estructura sin convertirse en juicio moral sobre el consumidor.

---

### Transición 2.2 → 2.3

```yaml
transicion_2_2_a_2_3:
  desde: caso_consumo_o_estatus
  hacia: caso_eleccion_profesional_o_vital
  operacion_de_paso: ampliar_de_consumo_a_identidad_vital
  estado_que_habilita: comprension_de_que_el_mecanismo_no_depende_del_producto
```

**Descripción protocolaria:**  
La transición debe ampliar la escala: el mecanismo no solo aparece en objetos comprados, también puede aparecer en decisiones que organizan identidad y vida.

---

## Subevento 2.3 — Caso de elección profesional o vital

```yaml
subevento_2_3:
  funcion_local: ampliar_el_mecanismo_a_decisiones_de_identidad
  estado_entrada: espectador_reconoce_el_mecanismo_en_consumo
  operacion_cognitiva: transferir_el_patron_a_decision_vital
  estado_salida: espectador_entiende_que_la_racionalizacion_puede_sostener_identidad
  modulos_MAANC:
    - modelador_de_situacion_cognitiva
    - analizador_de_relaciones_retoricas
```

**Descripción protocolaria:**  
Este subevento debe mostrar que decisiones aparentemente prácticas pueden estar atravesadas por identidad, miedo, expectativas familiares o deseo de reconocimiento.

**Criterio de validación:**  
Es correcto si el espectador ve que el mecanismo puede operar en elecciones de vida, no solo en compras.

---

### Transición 2.3 → 2.4

```yaml
transicion_2_3_a_2_4:
  desde: caso_eleccion_profesional_o_vital
  hacia: caso_ideologia_o_pertenencia
  operacion_de_paso: pasar_de_identidad_personal_a_identidad_grupal
  estado_que_habilita: apertura_a_creencias_y_pertenencias
```

**Descripción protocolaria:**  
La transición debe mover el mecanismo desde la identidad individual hacia las creencias, grupos o pertenencias colectivas.

---

## Subevento 2.4 — Caso de ideología o pertenencia grupal

```yaml
subevento_2_4:
  funcion_local: mostrar_racionalizacion_en_creencias_o_pertenencias

  modulos_MAANC:
    - analizador_argumentativo
    - analizador_intencional_atencional
```

**Descripción protocolaria:**  
Este subevento debe mostrar que un argumento puede ser racionalmente formulado y, al mismo tiempo, cumplir una función de pertenencia o defensa identitaria.

**Criterio de validación:**  
Es correcto si no invalida los argumentos, sino que abre la pregunta por la función que cumplen.

---

```yaml
transicion_2_4_a_2_5:

  operacion_de_paso: condensar_los_casos_en_forma_comun

```

**Descripción protocolaria:**  
La transición debe convertir la acumulación en abstracción. No basta con haber dado varios casos; debe extraerse la forma común.

## Subevento 2.5 — Abstracción del patrón general

```yaml
subevento_2_5:
  funcion_local: convertir_varios_casos_en_estructura
  estado_entrada: espectador_ha_visto_varios_casos_con_misma_forma
  operacion_cognitiva: extraer_macroestructura_comun
  estado_salida: espectador_preparado_para_formalizacion_psicologica
  modulos_MAANC:
    - extractor_de_macroestructura
    - detector_de_estructura_expositiva
```

**Descripción protocolaria:**  
Este subevento debe formular la estructura común de los casos. Es el puente hacia la formalización.

**Criterio de validación:**

# Evento Cognitivo 3 — Formalización psicológica basada en teorías existentes

```yaml

  nombre: formalizacion_psicologica_basada_en_teorias_existentes
  frase_guia: "No necesitamos inventar un nombre: varias teorías explican partes del mecanismo"
  funcion_macro: construir_un_modelo_psicologico_respaldado_por_bibliografia
```

## Descripción protocolaria del evento

Este evento convierte el patrón observado en un **modelo psicológico compuesto**. Su función es organizar varias líneas de investigación y usarlas para explicar la estructura común vista en los Eventos Cognitivos 1 y 2.

El evento debe mostrar que el fenómeno puede entenderse mediante la articulación de procesos ya estudiados en la literatura: opacidad introspectiva, afecto como orientación decisional, razonamiento motivado, justificación posterior, estabilización postdecisional, razones socialmente declarables y función lingüística de la explicación.

La fórmula operativa que debe quedar disponible para los eventos posteriores es:

```txt
estado afectivo / simbólico / identitario
→ orientación de la decisión
→ necesidad de explicación
→ razón declarable
→ estabilización o defensa de la decisión
```

## Estado cognitivo de entrada

```txt
El espectador reconoce varios casos con una forma común, pero aún no posee un modelo psicológico explícito ni respaldado.
```

## Estado cognitivo de salida

```txt
El espectador entiende un modelo psicológico de doble capa: una capa afectiva, simbólica o identitaria puede orientar la decisión, y una capa verbal o argumentativa puede justificar, comunicar o estabilizar esa decisión.
```

## Regla de construcción

Este evento debe formalizar sin presentar un nombre no académico como concepto consolidado. Debe apoyarse en teorías existentes, pero sin convertirse en revisión bibliográfica pesada. La teoría debe sentirse como explicación rigurosa de lo que el espectador ya vio en los casos.

```yaml
    descripcion: no_debe_saltarse_de_un_estado_a_otro_sin_operacion_de_paso

    descripcion: el_guion_no_debe_culpar_al_consumidor_ni_a_la_audiencia
```

# 11. Fórmula final del protocolo

```txt
No generar contenido por inspiración libre.
Instanciar material dentro de una arquitectura.
Cada parte existe por una función.
Cada función transforma un estado cognitivo.
Cada transformación habilita una transición.
Cada transición conserva la macrotrayectoria del guion.
```

---

# 12. Cierre

Este prompt protocolario sirve para convertir la estructura expandida del guion en una herramienta de construcción controlada. Su función es permitir que una IA, al recibir material del usuario, sepa **dónde colocarlo, qué función debe cumplir, qué transición debe habilitar y cómo validar si pertenece correctamente a la arquitectura**.

El resultado esperado no es generación libre, sino **instanciación estructural**.
