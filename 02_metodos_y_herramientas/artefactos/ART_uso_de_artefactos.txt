El artefacto captura esos archivos. La IA reconstruye la estructura conceptual a partir del artefacto.\n\n---\n\n## 2. Qué es un artefacto\n\nUn **artefacto** es una representación serializada de un proyecto textual.\n\nNormalmente se genera recorriendo una carpeta raíz y convirtiendo cada archivo textual en un registro estructurado.\n\nEl artefacto permite transportar un proyecto completo como un solo archivo de texto, normalmente en formato:\n\n```txt\nNDJSON\nJSONL\nTXT con líneas JSON\n```\n\nCada línea representa un archivo o un fragmento de archivo.\n\nEl artefacto no sustituye al proyecto original. Es una **fotografía estructurada** del proyecto en un momento determinado.\n\n---\n\n## 3. Función del artefacto\n\nEl artefacto cumple varias funciones:\n\n```txt\n1. Portabilidad\n   Permite compartir un proyecto completo como un solo archivo.\n\n2. Lectura por IA\n   Permite que una IA reciba muchas carpetas y archivos sin necesidad de acceder al filesystem original.\n\n3. Trazabilidad\n   Conserva rutas, tamaños, hashes y fechas de modificación.\n\n4. Reconstrucción estructural\n   Permite inferir relaciones entre archivos por su path.\n\n5. Auditoría\n   Permite detectar duplicados, versiones, cambios y archivos grandes.\n\n6. Compactación cognitiva\n   Convierte un proyecto distribuido en un paquete legible como unidad.\n```\n\nEn un sistema de grafos documentales, el artefacto funciona como el medio de transporte del grafo.\n\n---\n\n## 4. El programa constructor de artefactos\n\nEl archivo `make-project-dump.cjs` es un programa de Node.js que recorre una raíz de proyecto, lee archivos textuales y genera un archivo NDJSON.\n\nUso básico:\n\n```bash\nnode make-project-dump.cjs\n```\n\nUso con raíz y salida explícitas:\n\n```bash\nnode make-project-dump.cjs --root ./mi-proyecto --out ART_mi_proyecto.txt\n```\n\nUso con seguimiento básico de `.gitignore`:\n\n```bash\nnode make-project-dump.cjs --root ./mi-proyecto --out ART_mi_proyecto.txt --follow-gitignore\n```\n\nUso con logging:\n\n```bash\nnode make-project-dump.cjs --root ./mi-proyecto --out ART_mi_proyecto.txt --verbose\n```\n\n---\n\n## 5. Opciones del constructor\n\nEl programa acepta estas opciones:\n\n```txt\n--root <ruta>\n  Directorio raíz a escanear.\n  Default: .\n\n--out <ruta>\n  Archivo de salida NDJSON.\n  Default: project-dump.jsonl\n\n--max-file-bytes <n>\n  Umbral para decidir si un archivo se emite completo o en chunks.\n  Default: 262144 bytes = 256 KiB\n\n--chunk-bytes <n>\n  Tamaño aproximado de cada chunk.\n  Default: 131072 bytes = 128 KiB\n\n--follow-gitignore\n  Intenta leer .gitignore del root y omitir patrones básicos.\n\n--verbose\n  Emite logs informativos a stderr.\n```\n\n---\n\n## 6. Forma de los registros del artefacto\n\nCuando un archivo es pequeño, el programa emite un registro de tipo `file`.\n\nEjemplo:\n\n```json\n{\n  \"path\": \"grafo_de_regiones/modelo_base_de_regiones.md\",\n  \"type\": \"file\",\n  \"lang\": \"md\",\n  \"mediaType\": \"text/markdown\",\n  \"size\": 1234,\n  \"sha256\": \"...\",\n  \"mtime\": \"2026-04-27T00:00:00.000Z\",\n  \"text\": \"contenido del archivo\"\n}\n```\n\nCampos principales:\n\n```txt\npath:\n  ruta relativa del archivo dentro del proyecto.\n\ntype:\n  tipo de registro: file o chunk.\n\nlang:\n  lenguaje inferido por extensión.\n\nmediaType:\n  tipo MIME aproximado.\n\nsize:\n  tamaño del archivo.\n\nsha256:\n  hash del archivo completo.\n\nmtime:\n  fecha de modificación.\n\ntext:\n  contenido textual.\n```\n\n---\n\n## 8. Chunking de archivos grandes\n\nSi un archivo supera el umbral de `--max-file-bytes`, el programa lo divide en chunks.\n\nEjemplo:\n\n```json\n{\n  \"path\": \"documento-largo.md\",\n  \"type\": \"chunk\",\n  \"lang\": \"md\",\n  \"mediaType\": \"text/markdown\",\n  \"size\": 900000,\n  \"sha256\": \"...\",\n  \"mtime\": \"2026-04-27T00:00:00.000Z\",\n  \"chunkIndex\": 0,\n  \"lineStart\": 1,\n  \"lineEnd\": 150,\n  \"offsetBytes\": 0,\n  \"text\": \"fragmento del archivo\"\n}\n```\n\nCampos adicionales para chunks:\n\n```txt\nchunkIndex:\n  índice del fragmento.\n\nlineStart:\n  primera línea incluida.\n\nlineEnd:\n  última línea incluida.\n\noffsetBytes:\n  posición aproximada en bytes dentro del archivo original.\n```\n\nEl programa intenta cortar los chunks en límites de línea para no romper el texto.\n\n---\n\n## 9. Qué hace y qué no hace el artefacto\n\n### El artefacto hace\n\n```txt\n- recorre archivos;\n- serializa contenido;\n- conserva rutas;\n- conserva metadatos;\n- permite transportar el proyecto;\n- permite lectura por IA;\n- permite reconstruir estructura documental.\n```\n\n### El artefacto no hace\n\n```txt\n- no interpreta semánticamente los archivos;\n- no crea nodos conceptuales por sí mismo;\n- no infiere aristas complejas;\n- no valida el grafo;\n- no reemplaza la estructura del proyecto;\n- no convierte automáticamente Markdown en Cytoscape.\n```\n\nLa semántica debe estar codificada en la estructura de carpetas, nombres de archivo, contenido Markdown y convenciones documentales.\n\n---\n\n## 10. Relación entre filesystem y grafo documental\n\nEl método parte de esta equivalencia práctica:\n\n```txt\ncarpeta / archivo\n  → unidad documental\n    → posible nodo del grafo\n```\n\nUna carpeta puede representar una región, agrupación o contenedor.\n\nUn archivo puede representar:\n\n```txt\n- nodo primario;\n- definición de región;\n- definición de campo;\n- valor posible;\n- arista explícita;\n- índice;\n- manifiesto;\n- protocolo;\n- instancia;\n- salida.\n```\n\nLa estructura física del proyecto se vuelve parte de la estructura cognitiva del sistema.\n\n---\n\n## 11. Forma general de definir grafos con carpetas y archivos\n\nUna estructura documental de grafo puede organizarse así:\n\n```txt\ngrafo_documental/\n  modelo_base.md\n  region_1/\n    definicion.md\n    campo_1/\n      definicion.md\n      valor_1.md\n      valor_2.md\n    campo_2/\n      definicion.md\n      valor_1.md\n      valor_2.md\n  region_2/\n    definicion.md\n    campo_1/\n      definicion.md\n      valor_1.md\n```\n\nLectura conceptual:\n\n```txt\nmodelo_base.md\n  = nodo primario o documento rector\n\nregion_1/definicion.md\n  = nodo de región\n\nregion_1/campo_1/definicion.md\n  = nodo de campo\n\nregion_1/campo_1/valor_1.md\n  = nodo de valor\n```\n\n---\n\n## 12. Forma instrumental de definir nodos\n\nEn los paquetes conceptuales, un nodo suele tener esta estructura lógica:\n\n```json\n{\n  \"address\": \"graph/node/<node_id>\",\n  \"content\": {\n    \"id\": \"<node_id>\",\n    \"label\": \"<nombre visible>\",\n    \"type\": \"<tipo_de_nodo>\",\n    \"definition_ref\": \"def/<node_id>\",\n    \"summary\": \"<resumen breve>\"\n  }\n}\n```\n\nCampos:\n\n```txt\naddress:\n  dirección documental del nodo.\n\nid:\n  identificador estable.\n\nlabel:\n  nombre legible.\n\ntype:\n  tipo funcional del nodo.\n\ndefinition_ref:\n  referencia a su definición extensa.\n\nsummary:\n  resumen breve del rol del nodo.\n```\n\nEn una estructura basada en Markdown, la misma lógica puede traducirse así:\n\n```md\n---\nid: campo_tono_editorial\nlabel: Tono editorial\ntype: campo\ndefinition_ref: ./definicion.md\nsummary: Campo que regula la cualidad editorial de la manifestación.\n---\n\n# Tono editorial\n\nDefinición extensa del campo.\n```\n\nO, si se prefiere evitar frontmatter, así:\n\n```md\n# Nodo: campo_tono_editorial\n\n## ID\ncampo_tono_editorial\n\n## Label\nTono editorial\n\n## Type\ncampo\n\n## Definition ref\n./definicion.md\n\n## Summary\nCampo que regula la cualidad editorial de la manifestación.\n\n## Definición\nDefinición extensa del campo.\n```\n\n---\n\n## 13. Forma instrumental de definir definiciones\n\nEn los paquetes conceptuales, las definiciones se separan del nodo.\n\nForma lógica:\n\n```json\n{\n  \"address\": \"def/<node_id>\",\n  \"content\": \"Definición extensa del nodo.\"\n}\n```\n\nEl nodo apunta a esa definición mediante:\n\n```txt\ndefinition_ref: def/<node_id>\n```\n\nRelación:\n\n```txt\ngraph/node/<node_id>\n  → definition_ref\n    → def/<node_id>\n```\n\nEn Markdown, esto puede traducirse de dos maneras.\n\n### Opción A: definición separada\n\n```txt\ncampo_tono_editorial/\n  nodo.md\n  definicion.md\n```\n\n`nodo.md` contiene metadatos breves.\n\n`definicion.md` contiene el desarrollo conceptual.\n\n### Opción B: definición integrada\n\n```txt\ncampo_tono_editorial/\n  definicion.md\n```\n\nEl mismo archivo contiene metadatos y definición.\n\nPara proyectos pequeños o medianos, la opción B es más simple. Para proyectos grandes, la opción A facilita separar índice y desarrollo.\n\n---\n\n## 14. Forma instrumental de definir aristas\n\nEn los paquetes conceptuales, una arista suele tener esta estructura lógica:\n\n```json\n{\n  \"address\": \"graph/edge/<edge_id>\",\n  \"content\": {\n    \"id\": \"<edge_id>\",\n    \"from\": \"<node_id_origen>\",\n    \"to\": \"<node_id_destino>\",\n    \"type\": \"<tipo_de_relacion>\",\n    \"rationale\": \"<justificacion>\"\n  }\n}\n```\n\nCampos:\n\n```txt\naddress:\n  dirección documental de la arista.\n\nid:\n  identificador estable de la arista.\n\nfrom:\n  nodo origen.\n\nto:\n  nodo destino.\n\ntype:\n  tipo de relación.\n\nrationale:\n  justificación de la relación.\n```\n\nLa forma conceptual es:\n\n```txt\nfrom --type--> to\n```\n\nEjemplo:\n\n```txt\ncampo_tono_editorial --belongs_to--> grafo_comparecencia_de_la_manifestacion\n```\n\nPero la arista debe conservar su justificación:\n\n```txt\nrationale:\n  El tono editorial pertenece a la comparecencia porque regula la forma en que la manifestación aparece discursivamente ante el receptor.\n```\n\n---\n\n## 15. Aristas implícitas y explícitas\n\nEn una estructura por carpetas, algunas aristas pueden inferirse del path.\n\n### Aristas implícitas\n\nEjemplo:\n\n```txt\ngrafo_de_regiones/\n  grafo_comparecencia/\n    campo_tono_editorial/\n      valor_pedagogico.md\n```\n\nPuede implicar:\n\n```txt\ngrafo_de_regiones contains grafo_comparecencia\ngrafo_comparecencia has_field campo_tono_editorial\ncampo_tono_editorial has_value valor_pedagogico\n```\n\nEstas aristas nacen de la jerarquía documental.\n\n### Aristas explícitas\n\nSon necesarias cuando la relación no es puramente jerárquica.\n\nEjemplos:\n\n```txt\ncampo_tono_editorial depends_on campo_publico_objetivo\nvalor_densidad_alta incompatible_with publico_frio\ncampo_jerarquia_grafica supports campo_estilo_de_titulares\n```\n\nEstas aristas deben documentarse en archivos específicos o en una sección dedicada.\n\n---\n\n## 16. Formas recomendadas para guardar aristas explícitas\n\nHay varias opciones.\n\n### Opción A: archivo único de aristas por grafo\n\n```txt\ngrafo_comparecencia/\n  definicion.md\n  aristas.md\n```\n\nEjemplo de `aristas.md`:\n\n```md\n# Aristas — grafo_comparecencia\n\n```json\n{\n  \"id\": \"campo_tono_editorial-belongs_to-grafo_comparecencia\",\n  \"from\": \"campo_tono_editorial\",\n  \"to\": \"grafo_comparecencia\",\n  \"type\": \"belongs_to\",\n  \"rationale\": \"El tono editorial pertenece a este grafo porque regula la comparecencia discursiva de la manifestación.\"\n}\n```\n```\n\nVentaja: simple y compacto.\n\nDesventaja: puede crecer demasiado.\n\n### Opción B: carpeta de aristas\n\n```txt\ngrafo_comparecencia/\n  definicion.md\n  aristas/\n    campo_tono_editorial-belongs_to-grafo_comparecencia.md\n    campo_jerarquia_grafica-supports-campo_estilo_de_titulares.md\n```\n\nVentaja: cada arista es auditable individualmente.\n\nDesventaja: más archivos.\n\n### Opción C: aristas junto al nodo origen\n\n```txt\ncampo_tono_editorial/\n  definicion.md\n  aristas_salida.md\n```\n\nVentaja: facilita leer qué relaciones salen de un nodo.\n\nDesventaja: dificulta ver el grafo completo.\n\nRecomendación general: para un proyecto en crecimiento, usar **Opción B** en grafos grandes y **Opción A** en grafos pequeños.\n\n---\n\n## 17. Tipos útiles de nodos\n\nUna taxonomía inicial de nodos podría ser:\n\n```txt\nmodelo_base\nregion\ncampo\nvalor\nagrupacion\ncriterio\nregla\ninstancia\nadaptador\ncodominio\nmanifestacion\n```\n\nPara grafos de regiones, los tipos mínimos serían:\n\n```txt\nmodelo_base_de_regiones\nregion\ncampo\nvalor\narista\n```\n\nEjemplo:\n\n```txt\nmodelo_base_de_regiones.md\n  type: modelo_base_de_regiones\n\ngrafo_comparecencia/definicion.md\n  type: region\n\ngrafo_comparecencia/campo_tono_editorial/definicion.md\n  type: campo\n\ngrafo_comparecencia/campo_tono_editorial/valor_pedagogico.md\n  type: valor\n```\n\n---\n\n## 18. Tipos útiles de aristas\n\nUna taxonomía inicial de aristas podría incluir:\n\n```txt\ncontains\nhas_region\nhas_field\nhas_value\nbelongs_to\ndepends_on\nuses\nrefines\nspecializes\ngeneralizes\nsupports\nconstrains\nincompatible_with\ncompatible_with\nenables\nderives_from\nreferences\nprojects_to\n```\n\nPara un grafo documental de regiones, las más básicas serían:\n\n```txt\nhas_region\nhas_field\nhas_value\nbelongs_to\nreferences\ncompatible_with\nincompatible_with\ndepends_on\n```\n\nEjemplo:\n\n```txt\nmodelo_base_de_regiones --has_region--> grafo_comparecencia\n\ngrafo_comparecencia --has_field--> campo_tono_editorial\n\ncampo_tono_editorial --has_value--> valor_pedagogico\n\ncampo_tono_editorial --depends_on--> campo_publico_objetivo\n```\n\n---\n\n## 19. Convenciones de identificadores\n\nPara que el artefacto sea legible por IA y portable a herramientas de grafo, los identificadores deben ser estables.\n\nRecomendaciones:\n\n```txt\n1. Usar minúsculas.\n2. Evitar espacios.\n3. Usar guion bajo o guion medio de forma consistente.\n4. No cambiar IDs una vez usados.\n5. Evitar nombres demasiado genéricos.\n6. Incluir prefijo si hay riesgo de colisión.\n```\n\nEjemplos:\n\n```txt\nregion_comparecencia_manifestacion\ncampo_tono_editorial\nvalor_tono_pedagogico_directo\nedge_campo_tono_editorial-has_value-valor_tono_pedagogico_directo\n```\n\nSi el sistema usará Cytoscape.js, los IDs deben poder mapearse a:\n\n```js\n{ data: { id, label, type, definition_ref, summary } }\n```\n\npara nodos, y:\n\n```js\n{ data: { id, source, target, type, rationale } }\n```\n\npara aristas.\n\n---\n\n## 20. Relación con Cytoscape.js\n\nLa estructura documental puede proyectarse a Cytoscape.js.\n\nContrato recomendado para nodos:\n\n```js\n{\n  data: {\n    id: \"campo_tono_editorial\",\n    label: \"Tono editorial\",\n    type: \"campo\",\n    definition_ref: \"grafo_comparecencia/campo_tono_editorial/definicion.md\",\n    summary: \"Regula la cualidad editorial de la manifestación.\"\n  }\n}\n```\n\nContrato recomendado para aristas:\n\n```js\n{\n  data: {\n    id: \"campo_tono_editorial-belongs_to-grafo_comparecencia\",\n    source: \"campo_tono_editorial\",\n    target: \"grafo_comparecencia\",\n    type: \"belongs_to\",\n    rationale: \"El tono editorial pertenece a la comparecencia porque regula la forma discursiva de aparición de la manifestación.\"\n  }\n}\n```\n\nAsí, el mismo proyecto puede servir para:\n\n```txt\n- documentación humana;\n- lectura por IA;\n- visualización en Cytoscape;\n- validación de consistencia;\n- navegación conceptual.\n```\n\n---\n\n## 21. Estructura recomendada para un grafo documental reutilizable\n\nPara construir otro grafo siguiendo este método, se puede usar esta estructura:\n\n```txt\nmi_grafo/\n  README.md\n  modelo_base.md\n  regiones/\n    region_1/\n      definicion.md\n      campos/\n        campo_1/\n          definicion.md\n          valores/\n            valor_1.md\n            valor_2.md\n        campo_2/\n          definicion.md\n          valores/\n            valor_1.md\n    region_2/\n      definicion.md\n  aristas/\n    edge_1.md\n    edge_2.md\n  manifiesto_grafo.md\n```\n\nUna variante más compacta:\n\n```txt\nmi_grafo/\n  modelo_base.md\n  region_1/\n    definicion.md\n    campo_1/\n      definicion.md\n      valor_1.md\n      valor_2.md\n  region_2/\n    definicion.md\n    campo_1/\n      definicion.md\n      valor_1.md\n  aristas.md\n```\n\nLa primera es más ordenada. La segunda es más rápida.\n\n---\n\n## 22. Manifiesto de grafo\n\nTodo grafo documental debería tener un archivo manifiesto.\n\nEjemplo:\n\n```txt\nmanifiesto_grafo.md\n```\n\nContenido recomendado:\n\n```md\n# Manifiesto del grafo\n\n## ID del grafo\nmi_grafo\n\n## Propósito\nExplicar qué organiza este grafo.\n\n## Nodo primario\nmodelo_base.md\n\n## Tipos de nodos permitidos\n- region\n- campo\n- valor\n- regla\n\n## Tipos de aristas permitidas\n- has_region\n- has_field\n- has_value\n- depends_on\n- compatible_with\n- incompatible_with\n\n## Reglas de path\nExplicar cómo se mapean carpetas y archivos a nodos.\n\n## Reglas de trazabilidad\nExplicar cómo seguir un valor hasta su región y modelo base.\n```\n\nEl manifiesto ayuda a que una IA interprete el artefacto correctamente.\n\n---\n\n## 23. Reglas de construcción\n\n### Regla 1: cada nodo debe tener identidad estable\n\nNo basta con crear un archivo. El archivo debe declarar su ID o permitir derivarlo claramente del path.\n\n### Regla 2: cada nodo importante debe tener definición\n\nLos nodos sin definición son difíciles de reutilizar.\n\n### Regla 3: cada arista no trivial debe tener justificación\n\nLas relaciones no evidentes deben explicar su `rationale`.\n\n### Regla 4: las aristas jerárquicas pueden ser implícitas\n\nRelaciones como región → campo → valor pueden inferirse del path si el manifiesto lo declara.\n\n### Regla 5: las aristas semánticas deben ser explícitas\n\nDependencias, compatibilidades, restricciones y equivalencias deben documentarse.\n\n### Regla 6: el artefacto no debe ser la única fuente\n\nEl filesystem del proyecto sigue siendo la fuente primaria. El artefacto es una serialización.\n\n### Regla 7: el proyecto debe poder reconstruirse mentalmente desde el artefacto\n\nLos paths y nombres deben ser suficientemente claros.\n\n---\n\n## 24. Flujo recomendado de trabajo\n\n```txt\n1. Diseñar la estructura de carpetas.\n2. Definir el nodo primario.\n3. Crear regiones.\n4. Crear campos.\n5. Crear valores.\n6. Compartir el artefacto con una IA.\n11. Pedir validación estructural.\n12. Corregir paths, nodos, aristas o definiciones.\n```\n\n---\n\n## 25. Ejecución del artefacto\n\nDesde la raíz del proyecto:\n\n```bash\nnode make-project-dump.cjs --root ./mi_grafo --out ART_mi_grafo.txt --verbose\n```\n\nSi el constructor está en la raíz del proyecto completo:\n\n```bash\nnode make-project-dump.cjs --root ./sistema-de-transferencia --out ART_sistema_de_transferencia.txt --verbose\n```\n\nSi se quiere solo una subcarpeta:\n\n```bash\nnode make-project-dump.cjs --root ./sistema-de-transferencia/grafo_de_regiones --out ART_grafo_de_regiones.txt --verbose\n```\n\n---\n\n## 26. Cómo debe leer una IA el artefacto\n\nUna IA debe interpretar el artefacto en tres niveles.\n\n### Nivel 1: lectura documental\n\n```txt\n¿Qué archivos existen?\n¿Qué contiene cada archivo?\n¿Qué rutas tienen?\n```\n\n### Nivel 2: lectura estructural\n\n```txt\n¿Qué rutas implican jerarquías?\n¿Qué archivos son nodos?\n¿Qué archivos son definiciones?\n¿Qué archivos son aristas?\n```\n\n### Nivel 3: lectura semántica\n\n```txt\n¿Qué significa cada nodo?\n¿Qué relaciones existen?\n¿Qué restricciones o compatibilidades aparecen?\n¿Qué partes están incompletas?\n```\n\nEl artefacto ofrece la materia prima. La IA reconstruye el grafo usando las convenciones.\n\n---\n\n## 27. Errores frecuentes\n\n### Error 1: confundir artefacto con grafo\n\nEl artefacto transporta el grafo documental, pero no es el grafo en sí.\n\n### Error 2: crear archivos sin IDs estables\n\nSi los nombres cambian constantemente, la trazabilidad se rompe.\n\n### Error 3: depender solo de jerarquía\n\nLa jerarquía sirve para aristas básicas, pero no basta para relaciones complejas.\n\n### Error 4: duplicar definiciones\n\nSi el mismo campo se redefine en muchas partes, el sistema pierde coherencia.\n\n### Error 5: no justificar aristas semánticas\n\nUna arista sin `rationale` puede volverse opaca.\n\n### Error 6: mezclar nodos y ejemplos\n\nUna cosa es definir un valor posible; otra cosa es usar ese valor en una instancia.\n\n### Error 7: no tener manifiesto\n\nSin manifiesto, cada lector debe adivinar cómo interpretar la estructura.\n\n---\n\n## 28. Patrón general reusable\n\nEl método puede resumirse así:\n\n```txt\nfilesystem estructurado\n  + archivos Markdown con definiciones\n  + convenciones de nodos\n  + convenciones de aristas\n  + manifiesto\n  + constructor de artefacto\n  = grafo documental portable\n```\n\nY el flujo de uso:\n\n```txt\ncrear grafo en carpetas\n  → ejecutar make-project-dump.cjs\n    → obtener ART_*.txt\n      → compartir artefacto\n        → IA reconstruye y analiza\n```\n\n---\n\n## 29. Definición final\n\nUn **artefacto** es una serialización textual de un proyecto documental, producida mediante un programa que recorre archivos, conserva paths, metadatos y contenido, y emite registros NDJSON.\n\nUn **grafo documental** es una estructura de conocimiento construida mediante carpetas y archivos que representan nodos, definiciones y aristas.\n\nEl método conjunto consiste en construir grafos documentales dentro del filesystem y luego convertirlos en artefactos portables para que puedan ser leídos, auditados, refinados o implementados por humanos, IA o herramientas de visualización.\n\n---\n\n## 30. Fórmula de cierre\n\n```txt\nProyecto documental\n  → carpetas y archivos\n    → nodos, definiciones y aristas\n      → artefacto NDJSON\n        → lectura por IA\n          → reconstrucción del grafo\n            → validación / visualización / reutilización\n```\n\nEste método permite convertir conocimiento distribuido en una estructura portable, auditable y preparada para futuros sistemas de grafo.\n"}

Propósito del documento\n\nEste documento describe, de forma autosuficiente, el proceso correcto para convertir una definición textual o Markdown en un **artefacto materializable** que represente un **grafo documental**.\n\nEl proceso sirve para tomar una definición estructurada —por ejemplo una dimensión con campos, valores, restricciones y relaciones internas— y transformarla en un conjunto de archivos JSON organizados en carpetas, listos para ser materializados desde un JSONL mediante un script como `materialize-src-from-jsonl.cjs`.\n\nEl objetivo es que una definición pueda convertirse en una estructura de grafo explícita, navegable, validable y compatible con herramientas posteriores como Cytoscape.\n\nLa conversión debe producir tres tipos de objetos internos:\n\n```txt\ngraph/node/*\ndef/*\ngraph/edge/*\n```\n\nPero estos nombres **no deben convertirse en carpetas físicas principales**. Son namespaces internos escritos dentro de cada archivo JSON mediante el campo `address`.\n\nLa regla central del proceso es:\n\n```txt\nLa carpeta organiza físicamente.\nEl address interno clasifica semánticamente.\nLa arista explicita la relación.\nEl id absoluto evita colisiones.\n```\n\n---\n\n## 1. Qué es un artefacto materializable\n\nUn **artefacto materializable** es un archivo JSONL donde cada línea representa un archivo que será creado en una ruta específica.\n\nCada línea debe tener, como mínimo:\n\n```json\n{\n  \"path_rel\": \"ruta/fisica/del/archivo.json\",\n  \"content\": \"contenido del archivo\"\n}\n```\n\nEl campo `path_rel` indica dónde se materializará físicamente el archivo.\n\nEl campo `content` contiene el texto completo que se escribirá en ese archivo.\n\nEjemplo:\n\n```json\n{\n  \"path_rel\": \"grafo_de_regiones/grafo_ejemplo/campo_x/campo_x.json\",\n  \"content\": \"{\\n  \\\"address\\\": \\\"graph/node/grafo_de_regiones-grafo_ejemplo-campo_x\\\",\\n  \\\"content\\\": { ... }\\n}\"\n}\n```\n\nAl materializarlo, se crea:\n\n```txt\ngrafo_de_regiones/\n  grafo_ejemplo/\n    campo_x/\n      campo_x.json\n```\n\nDentro del archivo físico aparece el objeto de grafo.\n\n---\n\n## 2. Distinción esencial: `path_rel` vs `address`\n\nEl proceso requiere separar dos planos.\n\n### 2.1. `path_rel`\n\n`path_rel` es la ruta física del archivo.\n\nResponde a la pregunta:\n\n```txt\n¿Dónde se va a guardar este archivo dentro del proyecto materializado?\n```\n\nEjemplo:\n\n```txt\ngrafo_de_regiones/grafo_construccion_del_caso/construccion_conceptual/construccion_conceptual.json\n```\n\nLa ruta física debe seguir la estructura conceptual de la definición.\n\n### 2.2. `address`\n\n`address` es la dirección interna del objeto grafo-documental.\n\nResponde a la pregunta:\n\n```txt\n¿Qué tipo de objeto de grafo contiene este archivo?\n```\n\nEjemplos:\n\n```txt\ngraph/node/<id>\ndef/<id>\ngraph/edge/<id>\n```\n\nEl `address` no define la carpeta física. Solo clasifica internamente el contenido.\n\n### 2.3. Regla de separación\n\nCorrecto:\n\n```txt\npath_rel:\n  grafo_de_regiones/grafo_x/campo_y/valor_z/valor_z.json\n\naddress:\n  graph/node/grafo_de_regiones-grafo_x-campo_y-valor_z-valor_z\n```\n\nIncorrecto:\n\n```txt\npath_rel:\n  grafo_de_regiones/grafo_x/graph/node/valor_z.json\n```\n\nNo se deben materializar carpetas principales `graph/node`, `graph/edge` o `def`.\n\n---\n\n## 3. Error que este proceso evita\n\nUna conversión incorrecta crea esta estructura:\n\n```txt\ngrafo_de_regiones/\n  grafo_x/\n    graph/\n      node/\n      edge/\n    def/\n```\n\nEsto es incorrecto para este método, porque confunde los namespaces internos del grafo con carpetas físicas.\n\nLa estructura correcta debe seguir la forma conceptual de la definición:\n\n```txt\ngrafo_de_regiones/\n  grafo_x/\n    dimension_x.json\n    def_dimension_x.json\n\n    campo_a/\n      campo_a.json\n      def_campo_a.json\n\n      valor_1/\n        valor_1.json\n        def_valor_1.json\n        campo_a-has_value-valor_1.json\n\n    campo_b/\n      campo_b.json\n      def_campo_b.json\n```\n\nDentro de cada archivo `.json` aparece el `address` interno.\n\n---\n\n## 4. Estructura general de carpetas\n\nLa estructura física se construye a partir del recorrido conceptual de la definición.\n\nSi la definición tiene esta forma:\n\n```txt\ndimension_x\n  campo_a\n    valor_1\n    valor_2\n\n  campo_compuesto_b\n    campo_interno_b1\n      valor_3\n      valor_4\n```\n\nla estructura física debe ser:\n\n```txt\ngrafo_de_regiones/\n  grafo_x/\n    dimension_x.json\n    def_dimension_x.json\n    aristas_dimension_x.json\n\n    campo_a/\n      campo_a.json\n      def_campo_a.json\n      aristas_campo_a.json\n\n      valor_1/\n        valor_1.json\n        def_valor_1.json\n        campo_a-has_value-valor_1.json\n\n      valor_2/\n        valor_2.json\n        def_valor_2.json\n        campo_a-has_value-valor_2.json\n\n    campo_compuesto_b/\n      campo_compuesto_b.json\n      def_campo_compuesto_b.json\n      aristas_campo_compuesto_b.json\n\n      campo_interno_b1/\n        campo_interno_b1.json\n        def_campo_interno_b1.json\n        campo_compuesto_b-has_internal_field-campo_interno_b1.json\n\n        valor_3/\n          valor_3.json\n          def_valor_3.json\n          campo_interno_b1-has_value-valor_3.json\n\n        valor_4/\n          valor_4.json\n          def_valor_4.json\n          campo_interno_b1-has_value-valor_4.json\n```\n\nLa carpeta reproduce la forma de la definición. El contenido JSON declara el objeto grafo-documental.\n\n---\n\n## 5. Tipos de archivos\n\nUna conversión correcta puede producir tres tipos de archivos físicos.\n\n### 5.1. Archivo de nodo\n\nDeclara una entidad conceptual.\n\nEjemplo físico:\n\n```txt\ncampo_a/campo_a.json\n```\n\nContenido interno:\n\n```json\n{\n  \"address\": \"graph/node/grafo_de_regiones-grafo_x-campo_a\",\n  \"content\": {\n    \"id\": \"grafo_de_regiones-grafo_x-campo_a\",\n    \"label\": \"campo_a\",\n    \"type\": \"field_node\",\n    \"definition_ref\": \"def/grafo_de_regiones-grafo_x-campo_a\",\n    \"summary\": \"Resumen breve del campo.\"\n  }\n}\n```\n\n### 5.2. Archivo de definición\n\nDeclara la definición extensa de un nodo.\n\nEjemplo físico:\n\n```txt\ncampo_a/def_campo_a.json\n```\n\nContenido interno:\n\n```json\n{\n  \"address\": \"def/grafo_de_regiones-grafo_x-campo_a\",\n  \"content\": \"Definición extensa del campo_a.\"\n}\n```\n\n### 5.3. Archivo de arista\n\nDeclara una relación explícita entre dos nodos.\n\nEjemplo físico:\n\n```txt\ncampo_a/valor_1/campo_a-has_value-valor_1.json\n```\n\nContenido interno:\n\n```json\n{\n  \"address\": \"graph/edge/grafo_de_regiones-grafo_x-campo_a-has_value-grafo_de_regiones-grafo_x-campo_a-valor_1-valor_1\",\n  \"content\": {\n    \"id\": \"grafo_de_regiones-grafo_x-campo_a-has_value-grafo_de_regiones-grafo_x-campo_a-valor_1-valor_1\",\n    \"from\": \"grafo_de_regiones-grafo_x-campo_a\",\n    \"to\": \"grafo_de_regiones-grafo_x-campo_a-valor_1-valor_1\",\n    \"type\": \"has_value\",\n    \"rationale\": \"valor_1 es un valor declarado para campo_a.\"\n  }\n}\n```\n\n---\n\n## 6. Regla de IDs absolutos para nodos\n\nLos nodos no deben usar IDs cortos si esos IDs pueden repetirse en otros lugares.\n\nEjemplo incorrecto:\n\n```json\n{\n  \"address\": \"graph/node/construccion_conceptual\",\n  \"content\": {\n    \"id\": \"construccion_conceptual\"\n  }\n}\n```\n\nEjemplo correcto:\n\n```json\n{\n  \"address\": \"graph/node/grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual\",\n  \"content\": {\n    \"id\": \"grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual\"\n  }\n}\n```\n\n### 6.1. Fórmula del ID de nodo\n\nEl ID del nodo se construye a partir del recorrido conceptual completo:\n\n```txt\n<id> = grafo_de_regiones-grafo_de_region-subcarpeta-subcarpeta-nombre_de_nodo\n```\n\nDonde cada parte representa un segmento de la ruta conceptual.\n\n### 6.2. Relación entre `address` e `id`\n\nDebe cumplirse siempre:\n\n```txt\naddress = graph/node/<id>\ncontent.id = <id>\ndefinition_ref = def/<id>\n```\n\nEjemplo:\n\n```json\n{\n  \"address\": \"graph/node/grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual\",\n  \"content\": {\n    \"id\": \"grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual\",\n    \"label\": \"construccion_conceptual\",\n    \"type\": \"compound_field_node\",\n    \"definition_ref\": \"def/grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual\",\n    \"summary\": \"Campo compuesto estructural que explicita la composición de ideas activas que sostienen la realización.\"\n  }\n}\n```\n\n---\n\n## 7. Regla de IDs profundos\n\nCuando un nodo está profundamente anidado, el ID debe conservar todo el recorrido.\n\nEjemplo de nodo local:\n\n```txt\nformulacion_abierta_controlada\n```\n\nSi pertenece al recorrido:\n\n```txt\ngrafo_de_regiones/\n  grafo_construccion_del_caso/\n    construccion_conceptual/\n      coleccion_de_ideas_activas/\n        idea_activa/\n          formulacion_de_la_idea/\n            formulacion_abierta_controlada/\n              formulacion_abierta_controlada.json\n```\n\nentonces el ID correcto es:\n\n```txt\ngrafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea-formulacion_abierta_controlada-formulacion_abierta_controlada\n```\n\nY el nodo debe ser:\n\n```json\n{\n  \"address\": \"graph/node/grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea-formulacion_abierta_controlada-formulacion_abierta_controlada\",\n  \"content\": {\n    \"id\": \"grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea-formulacion_abierta_controlada-formulacion_abierta_controlada\",\n    \"label\": \"formulacion_abierta_controlada\",\n    \"type\": \"value_node\",\n    \"definition_ref\": \"def/grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea-formulacion_abierta_controlada-formulacion_abierta_controlada\",\n    \"summary\": \"Valor del campo formulacion_de_la_idea.\"\n  }\n}\n```\n\n### 7.1. Razón de la regla\n\nEsta regla evita colisiones.\n\nValores como:\n\n```txt\nbaja\nmedia\nalta\ncontraste\nmodular\nabierta_controlada\n```\n\npueden aparecer en muchos campos y grafos diferentes. Si se usan como IDs cortos, habrá errores al pasar el grafo a Cytoscape o a cualquier motor de grafo que requiera IDs únicos.\n\nPor tanto:\n\n```txt\nlabel = nombre legible local\nid = ruta conceptual completa\n```\n\n---\n\n## 8. Regla de IDs para definiciones\n\nToda definición debe apuntar al mismo ID absoluto del nodo que define.\n\nSi el nodo es:\n\n```txt\ngrafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual\n```\n\nentonces la definición debe ser:\n\n```json\n{\n  \"address\": \"def/grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual\",\n  \"content\": \"Definición extensa de construccion_conceptual.\"\n}\n```\n\nDebe cumplirse:\n\n```txt\nnode.content.definition_ref = def/<node.content.id>\ndef.address = def/<node.content.id>\n```\n\n---\n\n## 9. Regla de IDs absolutos para aristas\n\nLa misma lógica de IDs absolutos aplica a las aristas.\n\nUna arista no debe usar nombres locales cortos si sus nodos usan IDs absolutos.\n\n### 9.1. Fórmula general de arista\n\n```txt\nedge_id = <from_full_id>-<edge_type>-<to_full_id>\n```\n\nDebe cumplirse:\n\n```txt\naddress = graph/edge/<edge_id>\ncontent.id = <edge_id>\ncontent.from = <from_full_id>\ncontent.to = <to_full_id>\ncontent.type = <edge_type>\n```\n\n### 9.2. Ejemplo incorrecto\n\n```json\n{\n  \"address\": \"graph/edge/formulacion_de_la_idea-has_value-formulacion_abierta_controlada\",\n  \"content\": {\n    \"id\": \"formulacion_de_la_idea-has_value-formulacion_abierta_controlada\",\n    \"from\": \"formulacion_de_la_idea\",\n    \"to\": \"formulacion_abierta_controlada\",\n    \"type\": \"has_value\",\n    \"rationale\": \"...\"\n  }\n}\n```\n\nEsto es incorrecto porque `from` y `to` no son IDs absolutos.\n\n### 9.3. Ejemplo correcto\n\n```json\n{\n  \"address\": \"graph/edge/grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea-has_value-grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea-formulacion_abierta_controlada-formulacion_abierta_controlada\",\n  \"content\": {\n    \"id\": \"grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea-has_value-grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea-formulacion_abierta_controlada-formulacion_abierta_controlada\",\n    \"from\": \"grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea\",\n    \"to\": \"grafo_de_regiones-grafo_construccion_del_caso-construccion_conceptual-coleccion_de_ideas_activas-idea_activa-formulacion_de_la_idea-formulacion_abierta_controlada-formulacion_abierta_controlada\",\n    \"type\": \"has_value\",\n    \"rationale\": \"formulacion_abierta_controlada es un valor declarado para el campo formulacion_de_la_idea.\"\n  }\n}\n```\n\nAunque el ID de la arista sea largo, es seguro y no colisiona.\n\n---\n\n## 10. Rutas físicas de aristas\n\nLa ruta física de una arista puede ser más corta y más legible que su ID interno.\n\nEjemplo:\n\n```txt\ngrafo_de_regiones/grafo_construccion_del_caso/construccion_conceptual/coleccion_de_ideas_activas/idea_activa/formulacion_de_la_idea/formulacion_abierta_controlada/formulacion_de_la_idea-has_value-formulacion_abierta_controlada.json\n```\n\nPero dentro del archivo, la arista debe usar IDs absolutos:\n\n```json\n{\n  \"address\": \"graph/edge/<from_full_id>-has_value-<to_full_id>\",\n  \"content\": {\n    \"id\": \"<from_full_id>-has_value-<to_full_id>\",\n    \"from\": \"<from_full_id>\",\n    \"to\": \"<to_full_id>\",\n    \"type\": \"has_value\",\n    \"rationale\": \"...\"\n  }\n}\n```\n\nAsí se separan dos niveles:\n\n```txt\npath_rel:\n  navegación física humana\n\naddress/content.id:\n  identidad semántica absoluta del grafo\n```\n\n---\n\n## 11. Co-localización de aristas\n\nLa arista que integra un nodo hijo a su nodo padre debe colocarse cerca del nodo hijo.\n\n### 11.1. Campo a valor\n\n```txt\ncampo_a/\n  valor_1/\n    valor_1.json\n    def_valor_1.json\n    campo_a-has_value-valor_1.json\n```\n\n### 11.2. Campo compuesto a campo interno\n\n```txt\ncampo_compuesto/\n  campo_interno/\n    campo_interno.json\n    def_campo_interno.json\n    campo_compuesto-has_internal_field-campo_interno.json\n```\n\n### 11.3. Dimensión a campo\n\n```txt\ngrafo_x/\n  campo_a/\n    campo_a.json\n    def_campo_a.json\n    dimension_x-has_field-campo_a.json\n```\n\nLa co-localización permite leer el nodo hijo junto con la relación que lo integra.\n\n---\n\n## 12. Relaciones estructurales obligatorias\n\nToda relación estructural de la definición debe tener una arista explícita.\n\n### 12.1. Dimensión a campo\n\n```txt\ndimension_x --has_field--> campo_a\n```\n\n### 12.2. Campo compuesto a campo interno\n\n```txt\ncampo_compuesto --has_internal_field--> campo_interno\n```\n\n### 12.3. Campo a valor\n\n```txt\ncampo_a --has_value--> valor_1\n```\n\n### 12.4. Campo a estructura interna\n\n```txt\ncampo_a --has_structural_value--> estructura_b\n```\n\n### 12.5. Colección a tipo de ítem\n\n```txt\ncoleccion_x --has_item_type--> item_y\n```\n\n### 12.6. Entidad a componente requerido\n\n```txt\nidea_activa --has_required_component--> formulacion_de_la_idea\n```\n\n### 12.7. \"grafo_de_regiones-grafo_dimension_x-campo_b\"\n}\n```\n\nIncorrecto:\n\n```json\n{\n  \"from\": \"campo_a\",\n  \"to\": \"campo_b\"\n}\n```\n\nTambién incorrecto:\n\n```json\n{\n  \"from\": \"graph/node/grafo_de_regiones-grafo_dimension_x-campo_a\",\n  \"to\": \"graph/node/grafo_de_regiones-grafo_dimension_x-campo_b\"\n}\n```\n\n# 8. Cómo construir IDs\n\nLos IDs deben ser absolutos, estables y sin colisiones.\n\nLa regla recomendada es:\n\n```txt\nid = recorrido conceptual completo unido con guiones\n```\n\nEjemplo:\n\n```txt\ngrafo_de_regiones-grafo_dimension_x-campo_y\n```\n\nPara valores que se repiten en muchos campos, como `baja`, `media`, `alta`, no debes usar solo:\n\n```txt\nbaja\nmedia\nalta\n```\n\nDebes incorporar el recorrido completo.\n\nEjemplo:\n\n```txt\ngrafo_de_regiones-grafo_dimension_x-campo_y-baja-baja\n```\n\nLa duplicación final puede aparecer cuando la ruta física incluye una carpeta `baja/` y dentro un archivo `baja.json`. Lo importante es que el ID no colisione con otros valores llamados también `baja`.\n\nEjemplo:\n\n```txt\ngrafo_de_regiones-grafo_dimension_x-campo_a-baja-baja\ngrafo_de_regiones-grafo_dimension_x-campo_b-baja-baja\n```\n\nAmbos valores tienen label `baja`, pero IDs distintos.\n\n# 9. Cómo nombrar aristas\n\nLa regla recomendada es:\n\n```txt\nedge_id = <from_id>-<edge_type>-<to_id>\n```\n\nEjemplo:\n\n```txt\nfrom = grafo_de_regiones-grafo_dimension_x\nto   = grafo_de_regiones-grafo_dimension_x-campo_y\ntype = has_field\n```\n\nEntonces:\n\n```txt\nedge_id = grafo_de_regiones-grafo_dimension_x-has_field-grafo_de_regiones-grafo_dimension_x-campo_y\n```\n\nEl archivo físico de la arista puede tener un nombre más corto y legible:\n\n```txt\ndimension_x-has_field-campo_y.json\n```\n\nPero dentro del archivo, la arista debe usar IDs completos.\n\n# 10. Tipos de nodos recomendados\n\nCuando transformes una definición conceptual en grafo documental materializable, puedes usar tipos como:\n\n```txt\ndimension_node\nfield_node\ncompound_field_node\ninternal_field_node\nvalue_node\nexternal_reference_node\nconstraint_node\nmanifest_node\n```\n\nNo todos son obligatorios. Debes usarlos según la definición fuente.\n\nEjemplo:\n\n```txt\nUna dimensión principal → dimension_node\nUn campo directo → field_node\nUn campo compuesto → compound_field_node\nUn subcampo interno → internal_field_node\nUn valor cerrado u ordinal → value_node\nUna entidad mencionada pero no definida dentro de la dimensión → external_reference_node\n```\n\n# 11. Tipos de aristas recomendados\n\nLos tipos de aristas deben expresar relaciones estructurales o restricciones.\n\nTipos frecuentes:\n\n```txt\nhas_field\nhas_internal_field\nhas_value\nhas_definition\nmust_be_coherent_with\nmust_be_compatible_with\nmust_declare\nmust_not_include\nmust_not_be_confused_with\nmust_have_cardinality\nreferences_external\ndepends_on\nsupports\nconstrains\n```\n\nDebes evitar inventar relaciones innecesarias. Si una relación está claramente en la definición, represéntala. Si una entidad aparece mencionada pero no está definida como campo, crea una `external_reference_node`.\n\n# 12. Cómo transformar una definición en artefacto materializable\n\nCuando el usuario te dé una definición, debes seguir este procedimiento:\n\n```txt\n1. Identificar la dimensión raíz.\n2. Crear un nodo raíz de tipo dimension_node.\n3. Crear una definición para el nodo raíz.\n4. Identificar campos directos.\n5. Crear un nodo para cada campo directo.\n6. Crear una definición para cada campo directo.\n7. Crear aristas has_field desde la dimensión hacia cada campo.\n8. Identificar campos compuestos.\n9. Crear nodos para campos internos.\n10. Crear aristas has_internal_field.\n11. Identificar valores cerrados, semiabiertos u ordinales.\n12. Crear nodos value_node para cada valor.\n13. Crear definiciones para cada valor.\n14. Crear aristas has_value.\n15. Identificar restricciones explícitas.\n16. Convertir restricciones en aristas.\n17. Identificar entidades externas mencionadas por restricciones.\n18. Crear external_reference_node para entidades externas no definidas dentro de la dimensión.\n19. Crear definiciones para esas referencias externas.\n20. Validar todos los IDs.\n21. Validar todas las aristas.\n22. Emitir un JSONL con path_rel + content.\n```\n\n# 13. Estructura física recomendada\n\nLa estructura física debe seguir la estructura conceptual, pero sin usar `graph/node`, `graph/edge` ni `def` como carpetas.\n\nEjemplo:\n\n```txt\ngrafo_de_regiones/\n  grafo_dimension_x/\n    dimension_x.json\n    def_dimension_x.json\n\n    campo_a/\n      campo_a.json\n      def_campo_a.json\n      dimension_x-has_field-campo_a.json\n\n      valor_1/\n        valor_1.json\n        def_valor_1.json\n        campo_a-has_value-valor_1.json\n\n      valor_2/\n        valor_2.json\n        def_valor_2.json\n        campo_a-has_value-valor_2.json\n\n    campo_b/\n      campo_b.json\n      def_campo_b.json\n      dimension_x-has_field-campo_b.json\n\n    referencias_externas/\n      entidad_externa.json\n      def_entidad_externa.json\n```\n\n# 14. Forma exacta de una línea JSONL materializable\n\nCada línea del archivo `.jsonl` final debe verse así:\n\n```json\n{\n  \"path_rel\": \"grafo_de_regiones/grafo_dimension_x/campo_a/campo_a.json\",\n  \"content\": \"{\\n  \\\"address\\\": \\\"graph/node/grafo_de_regiones-grafo_dimension_x-campo_a\\\",\\n  \\\"content\\\": {\\n    \\\"id\\\": \\\"grafo_de_regiones-grafo_dimension_x-campo_a\\\",\\n    \\\"label\\\": \\\"campo_a\\\",\\n    \\\"type\\\": \\\"field_node\\\",\\n    \\\"definition_ref\\\": \\\"def/grafo_de_regiones-grafo_dimension_x-campo_a\\\",\\n    \\\"summary\\\": \\\"Campo directo declarado dentro de la dimensión X.\\\"\\n  }\\n}\"\n}\n```\n\nRecuerda:\n\n```txt\nEl archivo JSONL tiene un JSON por línea.\nEl campo content es un string.\nEse string puede contener JSON interno.\nEl materializador escribirá ese string como archivo físico.\n```\n\n# 15. Validaciones obligatorias antes de entregar el artefacto\n\nAntes de entregar un `.jsonl` materializable, debes validar:\n\n```txt\n1. Cada línea es JSON válido.\n2. Cada línea tiene path_rel.\n3. Cada línea tiene content.\n4. Cada content es string.\n5. Cada content que representa JSON interno es parseable como JSON.\n6. Ningún path_rel crea carpetas físicas graph/node, graph/edge o def.\n7. Todo nodo tiene address graph/node/<id>.\n8. Todo nodo tiene content.id igual al id del address.\n9. Todo nodo tiene definition_ref = def/<id>.\n10. Toda definición tiene address def/<id>.\n11. Toda definición corresponde a un nodo existente.\n12. Toda arista tiene address graph/edge/<edge_id>.\n13. Toda arista tiene content.id igual al edge_id.\n14. Toda arista tiene from y to.\n15. from y to apuntan a IDs de nodos existentes.\n16. from y to no usan labels locales.\n17. from y to no usan path_rel.\n18. from y to no incluyen graph/node/.\n19. Los IDs son absolutos y no colisionan.\n20. Los path_rel son únicos.\n```\n\n# 16. Errores que debes evitar\n\nEvita estos errores:\n\n```txt\n1. Confundir snapshot con artefacto materializable.\n2. Usar text en vez de content.\n3. Crear carpetas físicas graph/node, graph/edge o def.\n4. Usar labels cortos como IDs.\n5. Usar from/to con nombres locales.\n6. Usar from/to con address completo.\n7. Crear aristas hacia nodos inexistentes.\n8. Crear nodos sin definición.\n9. Crear valores no declarados por la definición fuente.\n10. Convertir ejemplos en valores cerrados cuando solo son ejemplos.\n11. Inventar campos que no aparecen en la definición.\n12. Omitir restricciones explícitas.\n13. No crear referencias externas para entidades mencionadas pero no definidas.\n14. Entregar una estructura conceptual sin generar el archivo JSONL.\n15. Entregar JSON normal en vez de JSONL.\n```\n\n# 17. Cómo debes responder cuando el usuario pida generar un artefacto materializable\n\nCuando el usuario diga algo como:\n\n```txt\nGenera el artefacto materializable para esta definición.\n```\n\nDebes hacer lo siguiente:\n\n```txt\n1. Comando esperado de materialización\n\nEl usuario materializará el artefacto con un comando como:\n\n```bash\nnode materialize-src-from-jsonl.cjs \\\n  --jsonl ART_nombre_del_artefacto_materializable.jsonl \\\n  --out ./prueba-materializacion\n```\n\nPor eso debes garantizar que el archivo generado sea compatible con `materialize-src-from-jsonl.cjs`.\n\n# 19. Definición final\n\nUn **artefacto materializable** es un archivo `.jsonl` donde cada línea describe un archivo que debe ser creado físicamente. Cada línea contiene una ruta relativa (`path_rel`) y un cuerpo de archivo (`content`). Cuando el contenido representa un grafo documental, cada archivo materializado puede contener un nodo, una definición o una arista. La estructura física se organiza mediante `path_rel`; la estructura semántica se organiza mediante `address`, `id`, `definition_ref`, `from`, `to`, `type` y `rationale`.\n\nLa fórmula completa es:\n\n```txt\ndefinición fuente\n  → análisis conceptual\n  → nodos\n  → definiciones\n  → aristas\n  → referencias externas\n  → registros JSONL con path_rel + content\n  → archivo .jsonl descargable\n  → materialize-src-from-jsonl.cjs\n  → filesystem real\n```\n\nTu objetivo no es solamente explicar esto. Tu objetivo es ser capaz de **producir correctamente** el `.jsonl` materializable cuando se te entregue una definición o una estructura fuente.\n"}
